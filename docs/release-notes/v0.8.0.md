# Release notes — v0.8.0

**Attribute providers.** A rule can now read the party *asking* — the principal's
department and clearance, the account's plan and region — and not only the object
being acted on:

```text
principal.kind == "user" && principal.department == object.department
account.plan == "enterprise"
```

Aperture is pre-1.0, so breaking changes land in a minor bump. This release
carries **three breaking signatures** (below) and — more importantly — **two
behaviour changes that produce no compile error at all**. Read those two even if
your build is green, because a green build is exactly what they look like.

These notes live under `docs/` but outside `docs/src/`, alongside
`docs/benchmarks.md`: they are repository prose, not a chapter of the book, and
they are deliberately absent from `docs/src/SUMMARY.md`. A release note describes
one transition between two versions; the book describes how Aperture works now.

## What is new

- **The attribute seam.** `provider.AttributeProvider` and
  `provider.AttributeRegistry` serve three closed **slots** — `user`, `machine`,
  `account` — each with its own provider and its own cache. See
  [Providers](../src/concepts/providers.md#attribute-providers).
- **`principal.*` is a real bag, and `account.*` is live.** The engine stamps a
  floor over whatever a host returns (`principal.{id, kind}`, `account.{id}`), so
  those keys are writable against any deployment, wired or not.
- **Two seed sections, both wiring.** `attributes:` lists bags inline;
  `attribute_providers:` points a slot at a CSV or at a `connections:` entry.
  Neither is model state: `Apply` writes no row and an export reproduces neither.
  See [Seed & portability](../src/concepts/seed.md#inline-subject-attributes).
- **Two loaders.** `csvprovider.NewAttributes` and `sqlprovider.NewAttributes`
  reuse the object loaders' value model exactly. Their keys are **bare** subject
  ids — `alice`, never `user:alice` — which is the one mistake nothing can catch.
- **A new evaluation note.** `attributes_floor_only` records that a rule read a
  host-defined field off `principal` or `account` while that root carried nothing
  but the floor, so every such comparison was false.
- **`Trace.Attributes`.** An `Explain` now reports the two bags the rules were
  evaluated against, values included — a deliberate disclosure, because *"why was
  this denied?"* is unanswerable when the deciding comparison was
  `principal.tier == "gold"` and the operator cannot see that the tier is
  `"silver"`. It reaches the MCP explain and simulate tools automatically, since
  their outputs are type aliases for `engine.Trace`.
- **`aperture attributes`.** `slots` (ungated) reports what is wired and how
  stale it may be; `query` and `invalidate` are system-tier. There is no RPC
  method and no MCP tool for the directory read, deliberately. See
  [Attributes (CLI)](../src/cli/attributes.md).
- **`service.ListAttributes`** and the three invalidation methods, gated directly
  through `authz.Gate.RequireSystemAdmin`.

## Breaking changes

All three are **source-level** breaks: they fail to compile, which is the good
kind. They are one change in three packages — a rule's evaluation environment now
needs to know *whose* attributes to read and *where*.

### 1. `scope.GrantContext` gained two fields

```go
type GrantContext struct {
	Pattern       identity.Pattern
	ObjectType    string
	Spec          Spec
	Account       string // NEW — the active account, bounding every attribute read
	PrincipalKind string // NEW — "user" / "machine"; empty means unknown, never a default
	Principal     string
	Action        string
}
```

They are struct fields rather than `context.Context` values on purpose: a missing
ctx value degrades silently to an empty account, which reads as "no attributes"
and therefore as a quiet allow-or-deny nobody wrote. A field is a compile-time
obligation on every caller.

**If you construct a `GrantContext`** (a custom scope strategy, a test helper),
fill in both. `PrincipalKind` may legitimately be empty when you do not have the
principal's record in hand — treat it as unknown, and never substitute a default,
or a machine principal gets answered for out of the human directory.

### 2. `scope.RuleEvaluator.Selected` gained two parameters

```go
// before
Selected(ctx context.Context, rule string, object identity.Identity, principal, action string) (bool, error)
// after
Selected(ctx context.Context, rule string, object identity.Identity, account, principalKind, principal, action string) (bool, error)
```

`rules.Engine` satisfies the new form. **If you implement `RuleEvaluator`
yourself**, add the two parameters; the account bounds any attribute lookup the
rule performs and the kind selects which attribute source answers for this
principal.

### 3. `rules.PrincipalResolver.Attributes` gained the kind

```go
// before
Attributes(ctx context.Context, principal string) (map[string]any, error)
// after
Attributes(ctx context.Context, kind, principal string) (map[string]any, error)
```

`kind` is `model.PrincipalKind`'s spelling carried as a string (`rules` imports no
`model`). It is what lets one resolver dispatch to a different source per kind
without re-deriving the kind from the id.

A resolver returns **only what the host knows**: it never has to publish `id` or
`kind`, and returning `nil` is not an error and not an empty root — it is exactly
the floor.

**New, not breaking:** `rules.AccountResolver` (`AccountAttributes(ctx, account)`)
and `rules.WithAccountResolver`. A `*provider.AttributeRegistry` satisfies both
seams, so one registry wires both.

## Behaviour changes

### `account.*` in a rule now compares real values

**Who is affected:** any deployment whose saved rules reference the `account`
root — `account.plan`, `account.region`, `account.tier`, anything but
`account.id`.

**What changed.** `account` has always been a legal variable root, so rules
referencing it have always validated and always compiled. What they did *not* do
is read anything: the evaluation environment hardcoded an empty map, so every
`account.<field>` comparison resolved against a missing key and evaluated
**false**, in every deployment, always.

As of v0.8.0 the `account` root is resolved from the **active account** — the
account the decision is being made in — through the attribute registry's
`account` slot. A rule that quietly evaluated false now compares whatever the
host's account directory says.

**Why it needs a note.** There is no compile error and no test failure for this.
The rules are unchanged, the schema is unchanged, and nothing in the codebase can
detect that a rule's *meaning* moved. The only signal is this paragraph.

**What it can do to a decision.** In an `inclusive` grant the change is
allow-ward: a rule that never selected may now select, widening what the grant
reaches. In an `exclusive` grant selection means *excluded*, so the same change
is deny-ward: a rule that never excluded anything may now start excluding. Both
directions are live, and which one a given permission gets depends on its scope
strategy.

**What to do before upgrading.**

1. Find the affected rules — anything whose AST contains a variable path under
   `account` other than `account.id`.
2. For each, decide what it should mean now that it reads real data. A rule
   written against an `account` root that never answered was, in practice, a
   constant `false`; if that constant was load-bearing, the rule needs rewriting
   rather than re-reading.
3. Wire an account attribute provider only when you want those rules live. A
   deployment with no `account` slot registered keeps deciding exactly as before:
   the bag is the floor, `account.id` is the active account, and every
   host-defined field is absent — which is the pre-v0.8.0 behaviour for every
   field but `id`.

**What did not change.** `account.id` is the engine's floor and is stamped over
whatever a directory returns, so it still resolves to the active account and a
host directory carrying its own `id` column cannot shadow it. Decisions made at
platform scope (active account `*`) see the floor alone — the wildcard is never
an attribute key, and no provider is ever consulted about it.

### Under `become`, `principal.*` — including `principal.id` — is the target

**Who is affected:** any deployment that uses impersonation in `become` mode
(`CheckAs` / `EnumerateAs` / `ExplainAs`, `aperture impersonate --mode become`)
**and** has a rule-backed scope strategy reading the `principal` root.

**What changed.** A `become` session has always resolved a decision over the
target's subject set alone — the target's grants, as if the target had asked.
What it *also* did was tell the rule layer about the **operator**: the
`GrantContext` carried `req.Principal`, so `principal.id` was the operator's id
and the principal kind was reported as unknown (empty).

As of v0.8.0 a `become` decision tells the rule layer about the **target**:
`principal.id` is the target's id, and the target's kind picks the attribute slot
`principal.tier` / `principal.clearance` / `principal.department` are read from.
`augment` is unchanged and continues to describe the **operator**, which is what
that mode means — the operator borrows grants while acting under its own
identity.

**Why it needs a note.** This is a deliberate behaviour change, not a bug fix.
While `principal` was `{"id": …}` and nothing read it, describing the operator
was an oversight cheap enough to ignore. Once the bag carries host attributes it
produces a decision whose *grant set* is the target's and whose *rule* is about
the operator — an authorization-bug surface that is invisible in a trace unless
you already suspect it. The pre-v0.8.0 spelling was also strictly worse than it
looked: an empty kind selects no attribute slot at all, so every rule under
`become` saw the floor bag and every `principal.<field>` comparison was false.

**What it can do to a decision.** Both directions are live, and which one you get
depends on the scope strategy. In an `inclusive` grant a rule that never selected
under `become` may now select, widening what an impersonated session reaches. In
an `exclusive` grant selection means *excluded*, so the same change is deny-ward.
A rule comparing `principal.id` against object metadata (`principal.id ==
object.owner`) flips from "does the operator own it" to "does the target own it"
— which, under a mode whose whole meaning is "as if the target had asked", is the
question that was intended.

**What to do before upgrading.** Review any rule referenced by a scope strategy
that reads the `principal` root, and confirm it reads correctly when the subject
is the impersonated target. If a rule was written to recognise the operator
specifically, it needs rewriting: `become` no longer offers a way to see the
operator from inside a rule, by design.

**What did not change.**

- **Audit.** `Decision.Impersonation` / `Trace.Impersonation` still record the
  real actor, the effective subject, the mode and the expiry, and
  `Trace.Request.Principal` is still the operator. The rule sees whose authority
  answered; the audit trail sees who acted.
- **Inert and expired sessions.** They confer no elevation and resolve
  byte-for-byte as the plain `Check` / `Enumerate` — including reading the
  operator's own attributes and never touching the target's.
- **The account boundary.** A cross-account session still fails closed, and it
  does so *before* any attribute is fetched, so a refused session is not a way to
  read another account's directory.
- **Cost.** Nothing extra is read. The target's kind arrives on the subject-set
  expansion the `become` path already performs, so a `become` decision still
  reads exactly one principal row.

## Two things to know before you wire a directory

Both are properties nothing in Aperture can enforce, which is why they are here
rather than in a test.

**A principal bag is global.** An attribute fetch is keyed by the bare principal
id alone and carries no account, so one principal's bag is visible to rules
evaluating in **every** account that principal is a member of. Keep principal
attributes account-neutral; per-tenant facts belong on the `account` slot, which
*is* bounded. Aperture cannot detect a violation — the values are opaque host
data, and a rule comparing them is doing exactly what it was written to do.

**A slot's `ttl:` is the window a revoked clearance keeps authorizing for.** An
object's metadata going stale is usually tolerable; an attribute bag is the
asker's *standing*. Pick each slot's TTL for how fast its revocations must land,
and close the window explicitly with `aperture attributes invalidate` when you
cannot wait. Invalidation is process-local and cannot reach a running
`aperture serve` — the controls there are the slot's TTL and a restart.

## Upgrade checklist

1. **Rebuild.** Fix the three signatures above if you implement any of them.
2. **Audit `account.*` rules** — anything but `account.id` changed meaning.
3. **Audit rules read under `become`** — `principal.*`, including `principal.id`,
   now describes the target.
4. **Decide slot by slot** whether to wire a directory. Wiring nothing keeps
   every decision exactly as it was.
5. **Set each slot's `ttl:` deliberately** once you do wire one.
6. **Check that a SQL or CSV attribute source keys on BARE ids** — an
   identity-shaped key produces a slot that silently never answers.
