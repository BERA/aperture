# Release notes — v0.8.0 (in progress)

Staging file for the `attribute-providers` effort. Each story that introduces a
change an operator must be told about appends a section here; the effort's
closing documentation story collects them into the published `v0.8.0` notes.

It lives under `docs/` but outside `docs/src/`, alongside `docs/benchmarks.md`:
it is repository prose, not a chapter of the book, and it is deliberately not
listed in `docs/src/SUMMARY.md`. A release note describes one transition between
two versions; the book describes how Aperture works now. Once v0.8.0 ships this
file has done its job.

## Behaviour changes

### `account.*` in a rule now compares real values

**Who is affected:** any deployment whose saved rules reference the `account`
root — `account.plan`, `account.region`, `account.tier`, anything but
`account.id`.

**What changed.** `account` has always been a legal variable root, so rules
referencing it have always validated and always compiled. What they did *not* do
is read anything: the evaluation environment hardcoded an empty map, so every
`account.<field>` comparison resolved against a missing key and evaluated
**false**, in every deployment, always.

As of v0.8.0 the `account` root is resolved from the **active account** — the
account the decision is being made in — through the attribute registry's
`account` slot. A rule that quietly evaluated false now compares whatever the
host's account directory says.

**Why it needs a note.** There is no compile error and no test failure for this.
The rules are unchanged, the schema is unchanged, and nothing in the codebase can
detect that a rule's *meaning* moved. The only signal is this paragraph.

**What it can do to a decision.** In an `inclusive` grant the change is
allow-ward: a rule that never selected may now select, widening what the grant
reaches. In an `exclusive` grant selection means *excluded*, so the same change
is deny-ward: a rule that never excluded anything may now start excluding. Both
directions are live, and which one a given permission gets depends on its scope
strategy.

**What to do before upgrading.**

1. Find the affected rules — anything whose AST contains a variable path under
   `account` other than `account.id`.
2. For each, decide what it should mean now that it reads real data. A rule
   written against an `account` root that never answered was, in practice, a
   constant `false`; if that constant was load-bearing, the rule needs rewriting
   rather than re-reading.
3. Wire an account attribute provider only when you want those rules live. A
   deployment with no `account` slot registered keeps deciding exactly as before:
   the bag is the floor, `account.id` is the active account, and every
   host-defined field is absent — which is the pre-v0.8.0 behaviour for every
   field but `id`.

**What did not change.** `account.id` is the engine's floor and is stamped over
whatever a directory returns, so it still resolves to the active account and a
host directory carrying its own `id` column cannot shadow it. Decisions made at
platform scope (active account `*`) see the floor alone — the wildcard is never
an attribute key, and no provider is ever consulted about it.

### Under `become`, `principal.*` — including `principal.id` — is the target

**Who is affected:** any deployment that uses impersonation in `become` mode
(`CheckAs` / `EnumerateAs` / `ExplainAs`, `aperture impersonate --mode become`)
**and** has a rule-backed scope strategy reading the `principal` root.

**What changed.** A `become` session has always resolved a decision over the
target's subject set alone — the target's grants, as if the target had asked.
What it *also* did was tell the rule layer about the **operator**: the
`GrantContext` carried `req.Principal`, so `principal.id` was the operator's id
and the principal kind was reported as unknown (empty).

As of v0.8.0 a `become` decision tells the rule layer about the **target**:
`principal.id` is the target's id, and the target's kind picks the attribute slot
`principal.tier` / `principal.clearance` / `principal.department` are read from.
`augment` is unchanged and continues to describe the **operator**, which is what
that mode means — the operator borrows grants while acting under its own
identity.

**Why it needs a note.** This is a deliberate behaviour change, not a bug fix.
While `principal` was `{"id": …}` and nothing read it, describing the operator
was an oversight cheap enough to ignore. Once the bag carries host attributes it
produces a decision whose *grant set* is the target's and whose *rule* is about
the operator — an authorization-bug surface that is invisible in a trace unless
you already suspect it. The pre-v0.8.0 spelling was also strictly worse than it
looked: an empty kind selects no attribute slot at all, so every rule under
`become` saw the floor bag and every `principal.<field>` comparison was false.

**What it can do to a decision.** Both directions are live, and which one you get
depends on the scope strategy. In an `inclusive` grant a rule that never selected
under `become` may now select, widening what an impersonated session reaches. In
an `exclusive` grant selection means *excluded*, so the same change is deny-ward.
A rule comparing `principal.id` against object metadata (`principal.id ==
object.owner`) flips from "does the operator own it" to "does the target own it"
— which, under a mode whose whole meaning is "as if the target had asked", is the
question that was intended.

**What to do before upgrading.** Review any rule referenced by a scope strategy
that reads the `principal` root, and confirm it reads correctly when the subject
is the impersonated target. If a rule was written to recognise the operator
specifically, it needs rewriting: `become` no longer offers a way to see the
operator from inside a rule, by design.

**What did not change.**

- **Audit.** `Decision.Impersonation` / `Trace.Impersonation` still record the
  real actor, the effective subject, the mode and the expiry, and
  `Trace.Request.Principal` is still the operator. The rule sees whose authority
  answered; the audit trail sees who acted.
- **Inert and expired sessions.** They confer no elevation and resolve
  byte-for-byte as the plain `Check` / `Enumerate` — including reading the
  operator's own attributes and never touching the target's.
- **The account boundary.** A cross-account session still fails closed, and it
  does so *before* any attribute is fetched, so a refused session is not a way to
  read another account's directory.
- **Cost.** Nothing extra is read. The target's kind arrives on the subject-set
  expansion the `become` path already performs, so a `become` decision still
  reads exactly one principal row.
